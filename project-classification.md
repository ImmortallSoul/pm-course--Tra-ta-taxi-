## 5.1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
| :--- | :--- | :--- |
| **Розмір проєкту** | `Малий` | Команда складається з 5 студентів, а тривалість розробки обмежена одним навчальним семестром. Обсяг робіт фокусується на MVP (мінімально життєздатному продукті). |
| **Тип продукту** | `Веб-застосунок` | Система створюється як адаптивний веб-застосунок (з використанням React). Це дозволить користувачам викликати таксі з будь-якого пристрою без необхідності завантаження у магазинах додатків. |
| **Галузь застосування** | `Транспорт / E-commerce` | Проєкт належить до сфери пасажирських перевезень та агрегаторів послуг, оскільки він з'єднує клієнта з постачальником послуги та передбачає онлайн-оплату. |
| **Рівень невизначеності вимог** | `Середній` | Базовий функціонал (замовлення, трекінг, оплата) є стандартним і зрозумілим. Проте технічні деталі реалізації інтеграції з картами та платіжними шлюзами можуть змінюватися в процесі розробки. |
| **Модель співпраці** | `Стартап / Внутрішній продукт` | Проєкт розробляється як власна ініціатива команди без конкретного зовнішнього замовника. Команда сама формує вимоги, спираючись на власне бачення ринку. |
| **Тип життєвого циклу** | `Гнучкий (Agile)` | Розробка вимагає швидкої адаптації. Ми плануємо ітеративно додавати функціонал: спочатку реєстрація, потім інтеграція карт, згодом система рейтингу та оплат. |

## 5.2. Аналіз внутрішнього оточення

* **👥 Склад і компетенції команди:** Команда з 5 осіб з чітким розподілом ролей. Основний стек розробки включає навички роботи з React (фронтенд), C# / .NET (бекенд) та реляційними базами даних (SQL Server / Oracle). 
* **💻 Наявні технічні ресурси:** Розробка ведеться на власних ПК/ноутбуках учасників. Використовуються безкоштовні середовища розробки (Visual Studio, VS Code), платформа GitHub для контролю версій та безкоштовні тарифи хмарних сервісів.
* **⏱️ Часовий бюджет команди:** Кожен учасник може виділити приблизно 10-15 годин на тиждень, оскільки робота над проєктом відбувається паралельно з іншими навчальними дисциплінами університету.
* **🧠 Досвід учасників:** Є міцні базові знання з об'єктно-орієнтованого програмування, проєктування БД та розробки веб-інтерфейсів, однак бракує комерційного досвіду створення систем реального часу.
* **🏛️ Організаційне середовище:** Навчальний процес у НУБіП. Комунікація відбувається через месенджери, а контроль виконання — через дедлайни здачі лабораторних робіт.

## 5.3. Аналіз зовнішнього оточення

* **🎯 Цільова аудиторія та її потреби:** Пасажири потребують швидкості подачі авто та прозорої ціни. Водії потребують зручного інтерфейсу для прийому замовлень та стабільного потоку клієнтів.
* **🏢 Наявні аналоги і конкуренти:** 
  * **Uklon** — сильний український гравець, має гнучку систему ціноутворення (можливість клієнту змінювати ціну) та програму лояльності.
  * **Bolt** — міжнародна компанія з агресивними знижками, інтегрована з сервісами оренди самокатів та доставки їжі.
* **🌐 Технологічні тренди:** Зростання частки безготівкових оплат (Google Pay, Apple Pay), використання геолокації в реальному часі високої точності, перехід на PWA (Progressive Web Apps).
* **⚖️ Регуляторні та правові чинники:** Законодавство України щодо пасажирських перевезень (вимоги до водіїв) та Закон про захист персональних даних (необхідність безпечного зберігання інформації користувачів).
* **🔌 Партнерські системи або API:** Критична залежність від сторонніх сервісів: картографічних API (Google Maps або Mapbox) для розрахунку відстаней і трекінгу, та платіжних систем (наприклад, LiqPay) для транзакцій.

## 5.4. Обмеження та припущення проєкту

### Обмеження
| № | Обмеження | Категорія |
| :-: | :--- | :---: |
| 1 | Проєкт має бути завершений до кінця поточного семестру (жорсткий дедлайн). | `Час` |
| 2 | Бюджет на розробку, ліцензії та інфраструктуру дорівнює нулю. | `Ресурси` |
| 3 | Дозволяється використання лише безкоштовних версій API (ліміт запитів до карт). | `Технології` |
| 4 | Розмір команди є фіксованим (5 осіб) без можливості залучення сторонніх фахівців. | `Ресурси` |

### Припущення
| № | Припущення | Обґрунтування |
| :-: | :--- | :--- |
| 1 | Усі учасники команди рівномірно розподілятимуть задачі та вкладатимуться в терміни. | Без відповідальності кожного учасника неможливо реалізувати проєкт в умовах обмеженого часу. |
| 2 | Безкоштовних лімітів API (карт та геолокації) вистачить для повноцінного тестування. | Навчальний проєкт тестуватиметься вузьким колом осіб і не генеруватиме промислового трафіку. |
| 3 | Обраний технологічний стек (React + C#) покриває всі потреби продукту. | Це сучасні технології, які мають велику кількість бібліотек для реалізації будь-якої бізнес-логіки. |
| 4 | Цільова аудиторія готова користуватися веб-застосунком замість встановлення нативного додатка. | PWA технології дозволяють веб-застосункам працювати так само швидко і зручно, як і нативним програмам. |

## 5.5. Висновки

> [!NOTE]
> Класифікація проєкту як малого стартапу з середнім рівнем невизначеності вимог прямо вказує на необхідність використання гнучких методологій управління (**Agile/Scrum**). Класична каскадна модель (Waterfall) тут не спрацює, оскільки інтеграція складних технологічних рішень (наприклад, API карт) вимагає ітеративного тестування і можливості змінювати архітектуру на ходу.

Найкритичнішими чинниками зовнішнього оточення є технологічна залежність від сторонніх API та наявність потужних монополістів на ринку (Uklon, Bolt). З внутрішнього оточення вирішальним є нульовий бюджет і жорсткі часові обмеження семестру. Це означає, що команда повинна зосередитися виключно на базовому функціоналі (**MVP**), відкинувши другорядні фічі.

> [!WARNING]
> **Критичні ризики проєкту:**
> * Вичерпання лімітів безкоштовних API може заблокувати процес тестування і розробки.
> * Нерівномірний розподіл зусиль через завантаженість команди іншими предметами.
> * Реалізація відстеження авто в реальному часі може виявитися технологічно складнішою, ніж очікувалося.

Враховуючи проведений аналіз, наступними кроками команди буде вибір конкретного постачальника картографічних послуг (з оцінкою безкоштовних тарифів), формування беклогу продукту (Product Backlog) та розподіл завдань на перший спринт. Також необхідно спроєктувати структуру бази даних для управління ролями (пасажир/водій), щоб розпочати практичну реалізацію.
